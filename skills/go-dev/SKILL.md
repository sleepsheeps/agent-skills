# Go 代码风格与工程规范（go-dev）

编写、修改、重构或审查 Go 代码时遵循以下原则，目标是写出**结构清晰、短小紧致、零冗余、易测可压**的 Go 代码。

## 1. 目录与包设计（Package Layout）

- **高内聚、单向依赖**：按业务领域或单一技术职责划分 package，拒绝 Java 式机械分层（`service/repository/controller`）；一个包只解决一类问题，禁止循环依赖。拆包时**状态字段与保护它的锁必须一起迁移**。
- **控制目录规模，大子系统收进子包**：单目录避免平铺超过 ~10 个源码文件；当某一边界清晰的子系统（如归档、路由、协议）自身包含 3~5+ 个文件时，应收拢为独立子 package，保持顶层目录清爽并天然做到可插拔。
- **沿用仓库既有布局**：新增包、入口或分层时，对齐目标仓库现有的目录结构和依赖方向，不另起炉灶。
- **跨模块复用收敛依赖**：供多处复用的基础包应保持依赖最简（尽量只依赖标准库），避免把业务状态或重依赖带进基础层。
- **命名克制、最小导出面**：包名用简短小写单词，不用下划线、不加复数、不与标准库重名；非跨包调用一律小写。

## 2. 文件拆分与命名规范

- **按职责拆，不按类型机械拆**：每个文件围绕一个清晰职责（如协议编解码、落盘写入、网络服务、指标定义、配置加载），一句话能说清它在干嘛；少建泛泛的 `types.go` / `helper.go` / `misc.go`。
- **篇幅适中**：单文件通常控制在 **100~300 行**；既不把所有逻辑塞进一个大 `main.go`，也不把每个小 struct 拆成满地 20 行碎文件。
- **文件命名**：全小写下划线（`snake_case`），名称与核心类型/职责一致；仅当同包存在多平台实现时才用 `*_linux.go` 后缀，单平台工具保持干净文件名并在文件头写 `//go:build linux`。
- **符号与变量命名**：
  - 避免“口吃”（导出名不重复包名，如 `archiveproto.Request` 而非 `ProtoRequest`）；Getter 不加 `Get` 前缀；布尔值用正向语义。
  - 哨兵错误 `ErrXxx/errXxx`，错误类型 `XxxError`；缩略词大小写统一（`ID/HTTP/TCP/FD/SQL/OSS`）。
  - 作用域决定长度：短循环用短名（`i/k/v`），结构体字段、参数与跨行变量用清晰名词；同一类型的方法接收者统一使用同一个 1~2 字母缩写，不用 `this/self`。
- **测试紧贴源码**：`foo.go` 对应 `foo_test.go`；纯逻辑单测与涉及磁盘/网络的集成测试分开组织。

## 3. 结构体、接口与函数设计

### 结构体（Struct）
- 字段按语义或并发归属分组，并在注释中标明锁保护边界或单协程归属（如 `// 以下字段仅在 mu 锁内访问`）。
- 尽量让零值有意义；依赖通过构造函数显式注入，避免隐式全局可变状态。
- 多字段初始化显式写字段名（每字段一行）；一两个字段的小结构体可紧凑书写。

### 接口与组件组装（Interface & Composition）
- **先 struct、后 interface**：默认使用具体类型和函数，绝不为只有单一实现的类型提前建“预留接口”。
- **调用方定义小接口**：只在真正需要多态、可插拔替换或测试隔离（如存储、传输、外部依赖）时，在**使用方**定义 1~3 个方法的窄接口。
- **入口显式组装**：各组件独立构造，在入口处显式拼装依赖，不在某个组件内部悄悄 `new` 死下游实现，保持单向依赖与可替换性。

### 函数与简洁度
- **先查 `go.mod` 版本底线**：改动前先看目标模块 `go.mod` 的 `go` 版本，只使用底线支持的标准库/语法特性；不为了语法糖擅自升级 `go` 版本，也不把低版本模块的合法老写法当坏味道。
- **写前克制（少写代码）**：动手前依次确认——是否真的需要 → 仓库里是否已有 → 标准库/OS 能力能否直接解决 → `go.mod` 已有依赖能否复用 → 能否一行写清 → 最小实现；若有意保留简化上限（如单锁/单连接），在代码处用一行注释说明边界。
- **短函数、单一职责**：主流程函数尽量控制在 **~40 行以内**（一屏读完）；超过 ~20 行的独立子逻辑，或出现 ≥2 次的同类代码块，抽成私有辅助函数。
- **短路早返回**：错误分支第一时间 `return`，保持主干逻辑贴左对齐、浅缩进。
- **消灭废话与造轮子**：
  - 禁止全分支同动作的空 `if` 判断（例如分支里和末尾都只是 `return`）。
  - 在 `go.mod` 版本允许前提下善用标准库新特性（如 `slices.Grow`、`binary.BigEndian.Append*`、`errors.Join`、`os.Root`、`min/max`、`range N`），不手写冗长的切片扩容、下标算术或冗余 `io.Writer` 循环写包装。
  - 资源申请后在短函数内立刻 `defer` 释放；启动任何 `go func()` 前必须明确其退出条件（`context` / 关闭 channel / `WaitGroup`），不留孤儿协程。
- **结构化日志**：小写英文消息 + 明确结构化字段（优先标准库 `log/slog`，或沿用项目已有日志库）；热路径靠指标不刷屏，关键生命周期与异常/拒绝分支须带上下文留痕（高频拒绝注意限频）。

### 并发、锁与停机规范
- **禁止在 `sync.Mutex` 内执行长阻塞网络/磁盘 I/O**：若需要串行化 I/O 且调用方携带 `context` 截止预算，改用可取消的 1 容量 channel 信号量（`select { case sem <- struct{}{}: ... case <-ctx.Done(): return ctx.Err() }`），并将保护内存快照的短锁与 I/O 互斥边界拆开，避免慢探活/慢切流阻塞状态读取与停机排空。
- **准入检查与在途登记必须共享同一同步边界**：禁止“无锁 `atomic.Bool` 预检 → 解码/准备 → `WaitGroup.Add(1)`”的 TOCTOU 竞态窗口；用 `sync.RWMutex` 在读锁内一次完成状态校验与在途计数 `+1` 后立刻放锁，再并发执行写盘/网络，切状态停收侧持写锁翻转后再等待在途归零。
- **禁止对可能超时的等待反复重用 `sync.WaitGroup`**：若 `Wait()` 外包了超时 `select`，超时返回后旧 `Wait()` 协程可能尚未结束，后续重新放行并调用 `Add(1)` 会直接触发 `sync: WaitGroup is reused before previous Wait has returned` runtime panic；可超时且可复用的在途排空必须改用锁保护计数器 + channel/`sync.Cond` 广播。
- **异步回调禁止直接读取可变结构体字段**：`context.AfterFunc`、`time.AfterFunc` 等不持锁并发运行的回调，注册前必须捕获局部不可变副本（如 `peer := r.conn`），防止与清理/重连并发导致 nil panic 或误关新连接。
- **停机等待必须有界、单调共享预算且不可逆**：
  - 强关 TCP socket 打不断阻塞在慢盘/死盘系统调用上的协程，`Close(timeout)` 强关连接后须设短收尾上界，不可无条件 `<-done` 死等；主入口（`Run`）等待任何后台子系统协程（如归档器/worker）退出也必须有界，被后台任务与主 I/O 路径共享的资源锁应支持 `ctx` 取消；
  - 停机多阶段（如在途收尾 + 排空循环，或主入口等待多个子系统收尾）共享同一个自取消时刻起算的总截止时间，不得各计各的预算导致总耗时翻倍；
  - `Close()` 后状态位不可再被异步翻回活跃；进程独占写入的数据目录/状态目录启动即加非阻塞 `flock(LOCK_EX|LOCK_NB)` 物理防双实例误挂。

### 资源、上下文与边界契约
- **禁用具名返回值配合 `defer` 清理资源**：`func open() (res *T, err error)` 中失败分支写 `return nil, err` 会先将具名变量置 `nil` 再执行 `defer`，导致句柄/连接静默泄漏；统一使用局部变量 + `ok := false; defer func() { if !ok { _ = res.Close() } }()`，成功返回前置 `ok = true`。
- **防长连接缓冲高水位膨胀**：长连接复用的 `[]byte` 禁止无上限单调扩容；超过常驻阈值（如 `256 KiB`）的大帧/大包改用 `sync.Pool` 按帧借还，避免偶发尖峰永久钉死堆内存。
- **`context` 派生与取消错误不吞不误判**：派生子 `ctx` 须继承父级 `Deadline()`（避免把 `DeadlineExceeded` 吞成 `Canceled`）；因本端取消强关连接导致的 `net.ErrClosed` 必须优先还原返回 `ctx.Err()`，严禁计入远端失败次数或触发熔断/冷却/切流。
- **批处理毒丸隔离与调度公平**：批量/归档循环遇到单个非法项或损坏文件须带上下文告警并跳过，不得拖垮同批或阻断后续健康任务；单协程事件循环内的发送/消费循环须设每轮让出上限（帧数或时间片），避免热源饿死事件、定时器与退出信号；轮转游标遇到跳过项后继续选中尾项时须锚定首个被跳过项防居中饿死。
- **配置 fail-fast 与跨层上限对齐**：只对未配置或 `0` 补默认值，负值、未展开 `${VAR}`、越界阈值及非法 `host:port`（含空端口）启动即报错；可选监听地址支持空串关闭时，必须在启动路径显式判断 `!= ""`，严禁透传给 `net.Listen` 静默绑随机端口；跨组件上限（如落盘文件名预留后缀、双端单帧上限）须对齐或可协商。

## 4. 中文注释规范

- 函数定义前统一使用中文注释，讲清**意图、前置条件、锁/生命周期约束**，不要把函数名机械翻译成中文：
  ```go
  /*
  * @brief 函数说明
  * @param 参数名 参数说明
  * @return 返回值说明
   */
  ```
- 简单无参或自解释函数可用单行 `/* @brief ... */` 保持紧致，避免注释比函数体更长。
- 关键常量、结构体字段归属与非显而易见的边界逻辑用简洁中文单行注释。

## 5. 测试覆盖与核心 Benchmark

- **通用单测与对抗用例设计**：编写或加固单测/集成/E2E 测试时，同步遵循 `unit-test` skill（覆盖率双标准、删修复必红自检、状态×路径矩阵、真实物理尺度、独立因果隔离与六维对抗清单）。
- **测试覆盖要求**：
  - 优先表格驱动测试（`t.Run` 命名子测试），覆盖：**正常路径、边界值、畸形/错误输入、并发竞态（`-race`）、资源上限与故障恢复**。
  - **测行为不测内部实现**：断言公开契约与可观测结果，不耦合私有实现细节；每条用例必须能拦截真实缺陷，禁止无意义断言（如常量自比）。
  - **覆盖率用来查盲区而非刷数字**：核心包语句覆盖率以 **80%+** 为参考，重点核查所有含状态转移、IO、并发与故障恢复的函数均无 `0%` 遗漏；不为了凑 `100%` 强测不可控底层错误或给简单 getter 写无意义断言。
  - **子测试隔离与防泄漏**：`t.Run` 内必须使用子测试自己的 `t`（禁止在循环外用父 `t` 构造断言器供子测试复用）；涉及后台 goroutine 的包须验证退出后无协程泄漏。
  - **确定性同步，禁止靠 `time.Sleep` 赌并发窗口**：并发竞态、在途取消、停机排空测试必须用 `channel` 栅栏、`net.Pipe()`、钩子回调或可控时钟精确卡住临界点，确保 `-race -count=2` 稳定必现、零抖动。
  - **消灭“假绿”测试**：测试中所有 I/O、编解码、遍历回调错误（`WriteFile`/`ReadResponse`/`ReadAll`/`json.Decode`/`WalkDir` 等）必须检查；断言清理/删除前先断言目标此前确实存在且非空；验证“不切流/不降级”须存在真实健康备节点；指标断言按完整指标名与标签解析，不做宽泛子串匹配。
- **核心函数 Benchmark**：
  - 对热路径函数（如协议编解码、文件行解析、合批调度、并发写盘）编写 `Benchmark*`，显式调用 `b.ReportAllocs()`（Go 1.24+ 模块优先用 `b.Loop()`），关注 `ns/op`、`B/op`、`allocs/op`，防止隐蔽内存分配与 GC 抖动。

## 6. 修改后验证门禁

> 只读分析（“看代码 / 分析一下 / 先别改”）时**不要**主动跑 `go test / vet / build`。  
> 禁止将 `GOCACHE` 或 `GOMODCACHE` 设在仓库目录内。

Linux 代码（Windows 环境下在 WSL2 执行）修改 `.go` 后必须执行：
1. `gofmt -w <改动包>`
2. `go vet <改动包>`
3. 竞态与逐函数覆盖率检查：`CGO_ENABLED=1 go test -race -coverprofile=/tmp/go-cover.out <改动包> && go tool cover -func=/tmp/go-cover.out`（WSL 默认可能为 `CGO_ENABLED=0`，跑 `-race` 需显式开启；用逐函数明细确认无核心逻辑 `0%` 盲区，需要看行级红绿高亮时可用 `go tool cover -html=/tmp/go-cover.out`）
4. 核心包基准测试：`go test -run=^$ -bench=. -benchmem <核心包>`
5. 按需静态构建检查：`CGO_ENABLED=0 go build -buildvcs=false <cmd路径>`

## 7. 分阶段推进与文档同步

- 复杂任务按阶段推进，每阶段通过门禁后停下来汇报核心文件、测试与基准结果，确认后再进下一阶段。
- 协议、配置、接口或目录行为变动时，同步更新设计/运维文档。
